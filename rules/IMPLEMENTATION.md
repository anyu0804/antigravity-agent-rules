# 诊断与施工切换

本文件细化全局§2A，不扩大授权。

用户已要求施工，证据足以选择可验证的实施方案，范围与授权明确时，开始最小修改与相关回归。故障修复依据根因证据；新增功能依据现状、目标与范围，不要求不存在的故障根因。

尚不能选择实施方案时，按全局§2 补齐有区分力的证据。方案已明确后的检查应实际影响修改方案、范围、安全、回滚或验收；复用已有有效证据，完成约定交付后结束。

缺少必要条件时说明具体卡点，继续不依赖它的已授权工作；按全局§4 / §7A 表达实际阻断原因。

## 前端与 UI 交付密度约束

当施工任务涉及前端页面、桌面端 GUI、Dashboard 看板或交互组件开发（尤其使用 `Gemini 4 Carbon` 生成界面）时，必须遵守以下结构与视觉密度限制：

- **限制组件与视觉容器嵌套层级（≤3 层）**：单个视图区域内带边框/背景色块的视觉容器嵌套（如 Card / Panel / Box / Collapse 套嵌）不得超过 **3 层**；优先使用留白（spacing）、字号层级与对齐关系组织信息，禁止“卡片套卡片再套内框”的过度包装。
- **控制首屏信息密度**：单行并列卡片不超过 **3–4 个**，单个卡片内的核心指标或操作项不超过 **3 项**；低频高级配置、次要诊断元数据与长篇日志默认折叠或下沉至二级详情抽屉/弹窗，禁止首屏平铺堆砌全部字段。
- **界面微文案去套话**：按钮、空状态提示与错误引导保持简练直白，避免机械排比与 AI 翻译腔。
- **对着画面验收**：UI 改动完成后实际启动页面或面板，截取主要状态（空状态、正常数据、报错态）回喂自查层级拥挤、对齐与状态切换是否生效，按截图结论修改后再交付；未经截图核对的视觉结论标 `NOT_PROVEN`。
