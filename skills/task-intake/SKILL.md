# Task Intake — 工程任务编译、状态机与交付协议（完整版）

> 本文件承载《全局规则》（`../../rules/AGENTS.md`）的多步骤工程任务编译、工作模式切换、状态标记总表（原全局 §7A）、异常熔断、独立 Review 与四态交付回报协议。
> 普通问答、简短解释或轻量修改自然作答，不套用本工程状态机。

## 1 目标与内部任务编译

把一句或多句自然语言翻译成一份内部任务定义（用户无需提供正式任务书），明确目标、对象、交付形式、授权范围、验收与停止条件。编译结果默认保存在内部，输出给用户的是执行过程摘要与最终回报。

- **工作模式（全局 §2）**：
  - **`FAST_PATH`（默认）**：故障根因明确且复现稳定时，`复现 → 最小诊断 → 修改 → 回归 → STOP`；其他清楚任务按交付要求直接做。
  - **`INVESTIGATION_PATH`（证据不稳或根因不清）**：先明确证据缺口，优先做有区分力的实验。在授权范围和用户预算内，只要仍产生有效新证据就继续，不按假设、实验或脚本数量强制结束。用户预算耗尽或已无可区分的新实验时，标 `NOT_CONVERGED`，停止该路径并报告证据与继续条件。

## 2 交付契约与工作对象

- **交付契约（全局 §5A）**：用户指定的文件、图片、代码、表格、文档或其他交付形式构成交付契约。参考已清楚时直接做，不用概念图、示意图、简化版、伪代码或近似实现替代。确实无法可靠完成原交付时标 `DELIVERY_BLOCKED`，说明已确认部分和缺失条件；未经用户接受，不以替代产物冒充完成。
- **输入与现场核实**：实现方式或技术路线不确定时，优先读取现场文件、文档和实际证据自行判断；能自行查证的问题不反问用户。现场事实与描述不同时，以实际证据为准并报告差异。
- **对接第三方运行时先读对方源码**：插件、扩展、跨进程桥接或读写第三方数据格式时，施工前先委派只读子代理阅读宿主/对方源码，确认加载时机、存档与写回时机、数据格式和并发写入行为，结论带 `文件:行号` 写入项目笔记后再动手；不凭训练记忆假设宿主行为，查不到源码的行为标 `HYPOTHESIS`。

## 3 授权与范围边界

- **允许范围**：项目目录内必需的读取、新建、修改、复制、移动（全局 §1“直接做”）；明确要求原地修改时先建可验证备份与回滚点（全局 §9）；运行项目既有构建、测试、校验脚本；同一对象和影响范围已获批准时不重复询问。
- **禁止范围**：未经授权扩大范围、删数据、改全局环境或进行不可逆操作（全局 §1“先问再动”）；不顺手重构、清理、升级依赖或修无关 warning；范围外问题只记录证据与影响，标 `OUT_OF_SCOPE_NOTED`。严禁把密钥、token、凭据写入文件或提交仓库。

## 4 验收标准与证据纪律

- 编译时确定**可实际验证的完成标准**：交付物存在、位置正确、内容/格式符合要求、必要测试通过。
- **外部宿主集成类任务验收先行**：插件、扩展、跨进程桥接等需要在真实宿主中运行的任务，施工前先把真实环境验收步骤写入项目根目录 `ACCEPTANCE.md`（启动什么、执行什么操作、在宿主端观察到什么算通过、失败时看哪份日志）。未在真实宿主跑通的层级只报 `NOT_PROVEN`；离线单测或独立探针全绿不得推出 `PASS`，需用户真机确认时标 `REQUIRES_MANUAL_OUT_OF_AGENT_VALIDATION`。
- 验证须执行交付物自身的入口：规则、模式、模板或脚本应实际加载或运行；另外写出的等价实现或独立探针不能替代目标产物验收。无法确认验收器是否真正消费目标产物时，用一个最小负向对照检验（原件只读）。
- 下载与落盘、独立探针通过、项目入口接入、真实环境运行分别说明，只把实际验证的一层标为通过。
- **Benchmark 字段要求**：须写清测试环境、测试对象、测试方法、样本数量、是否 Headless、是否禁用 GPU。

## 5 状态标记总表（原全局 §7A）

只在实际发生对应情形时使用下列标记，不为普通任务遍历状态表。结局、原因、证据和阶段分开表达；不另造同义状态：

- **工作模式**：`FAST_PATH` / `INVESTIGATION_PATH`
- **证据状态**：
  - `VERIFIED`：已通过实测或可靠证据复核；
  - `NOT_PROVEN`：证据不足或当前环境无法验证（不得猜测通过）；
  - `HYPOTHESIS`：待验证假设；
  - `EVIDENCE_CONFLICT`：可比版本、输入和条件下证据冲突且无法解释。
- **调查 / 验收状态**：
  - `NOT_CONVERGED`：调查未收敛且已无可区分的新实验或用户预算耗尽；
  - `GATE_FAILED`：修改完成后最终验收仍未达标（施工中途失败不算）。
- **阶段状态**：
  - `READY_FOR_REVIEW` / `READY_FOR_DEPLOYMENT_REVIEW`：等待必需的独立复核，不等于通过或可发布。
- **交付 / 范围 / 版本 / 续作**：
  - `DELIVERY_BLOCKED`：原交付条件不足；
  - `OUT_OF_SCOPE_NOTED`：范围外问题仅记录；
  - `SOURCE_VERSION_MISMATCH`：线上/外部来源与冻结基线不符；
  - `RESUME_FROM_CHECKPOINT`：中断后从有效现场续作。
- **验证缺项**：
  - `REQUIRES_MANUAL_OUT_OF_AGENT_VALIDATION`：需用户在真实桌面环境确认；若属必需验收，不报 `PASS` / `PASS_WITH_NOTES`。

## 6 异常与熔断处理

- **证据冲突（`EVIDENCE_CONFLICT`）**：确认冲突后暂停依赖争议证据的修改；保留全部相关结果，记录变化变量、仍可确认项和区分原因所需的最小实验。不得随机换 fixture 挑选通过结果、放宽门禁或堆诊断脚本。
- **门禁未达（`GATE_FAILED`）**：最终验收未达标时停止并报告实测与期望、失败证据；不宣布完成、部署或发布，不放宽判据或改断言求绿。
- **卡住与阻断**：重复同一失败路径已无新信息，或缺少必需输入/授权时，停止该路径，先完成不依赖阻断条件的已授权工作，再报告：
  ```text
  BLOCKED：原因（用 §5 最具体的状态标记）
  继续所需的最小条件：<一句话>
  ```

## 7 独立 Review 细则（原全局 §8）

- **触发范围**：真实存档、数据库或地图的格式转换与写回、批量破坏性操作、生产部署、Critical/High 风险修复及大范围重构需要独立 Review。普通文本导出、副本中的隔离实验和局部低风险编辑可自行验证。
- **执行纪律**：Reviewer 默认只读，核对完成声明、实际调用的产物与验证层级；关键边界有疑点时做有区分力的反例。Reviewer 优先使用与施工代理不同厂家或不同模型家族（如施工用 `Gemini 4 Carbon`，复核用 `Gemini 4 Argon` 或经 MCP 桥接的外部异构模型）；同一模型复核同一产物只记为自查。发现问题给 `Severity / Evidence / Failure Scenario / Minimum Fix`。
- **门禁**：必需复核未完成只报 `READY_FOR_REVIEW` 或 `READY_FOR_DEPLOYMENT_REVIEW`，不得报 `PASS`；自查不算独立复核。

## 8 最终四态回报协议（原全局 §15）

多步骤工程交付结束时使用以下四态之一置于回报开头，并报告完成内容、产物、验证结果、相关未验证项与实际风险（普通问答自然作答，不套用四态）：

| 结局 | 含义 |
| :--- | :--- |
| **`PASS`** | 交付、必需验收和复核均完成 |
| **`PASS_WITH_NOTES`** | 满足 `PASS`，另有不影响交付的说明 |
| **`BLOCKED`** | 必需工作或验证未完成；给具体原因与最小继续条件 |
| **`FAIL`** | 必需要求实测未达；给失败证据与恢复信息 |

- **修改型任务**：报告实际修改的文件、修改摘要（必要处给 Diff）、验证结果。
- **生成型任务**：报告实际生成的文件、输出路径、内容/格式摘要、验证结果。
- 当前任务完成后即停止，不固定追加“下一步建议”清单，不自行接着开展其他工作。
